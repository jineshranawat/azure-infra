RTT Engine · Command Centre

The single place to understand, run, deploy and extend “The 50 Problems, Solved” — the NHS RTT reference implementation. Read top-to-bottom to go from zero to PhD; jump to Deploy if you just want it live.

Who this is for

Clare (runs the PTL), engineers (own the pipeline), IG (Nitin), and anyone learning Foundry end-to-end.

Three artefacts, one story

Learning Journey teaches the platform · this manual documents the engine · the React app is the product it powers.

Use the left rail. Each level ends where the next begins. Deploy runbooks are literal click-by-click UI steps.

Follow one row: a CSV line lands as text → raw_ingest types it → clean_silver canonicalises the specialty, checks trust/PK/range/dates and either keeps it or quarantines it with a reason → sae_minimise strips IG columns → metrics stamps breach flags/RAG → security pseudonymises the NHS number → it becomes a Pathway object → the React app shows it on the PTL and lets Clare triage it.

L0 · Foundry in plain English

Dataset

A versioned table. Every build is an immutable transaction (time-travel + rollback for free).

Transform

Code that turns input datasets into output datasets. Ours are Python (Polars/Spark).

Branch

A safe workspace. We build on a feature branch, run checks, then merge to master.

Data Expectations

Checks embedded in transforms. FAIL blocks the build; WARN signals. Feeds Data Health.

Ontology

Turns rows into objects (Pathway, Trust) with links + actions — the semantic layer apps use.

OSDK

A typed SDK generated from the Ontology so a React app can read objects and run actions safely.

L1 · The medallion (why three layers)

Bronze keeps raw truth; Silver makes it correct and safe; Gold makes it useful. Separating them means a bug in analytics never corrupts raw data, and IG rules apply at exactly one gate.

LayerDatasetsJob
Bronzeraw, typedland + type; never drop rows
Silverclean, minimised, metricsvalidate, quarantine, minimise (IG), enrich
Goldtrust_specialty_perf, ptlaggregates + the PTL for Clare

Deep theory for every stage: see pipeline_explainer.html → Code flow.

L2 · Data quality & quarantine

The policy lives in one tested place (lib/dq_rules.add_reject_reason). Rows that fail any rule go to /quarantine with a reject_reason; a recon dataset proves clean + rejects = input (1215 = 1205 + 10). Nothing is ever silently dropped.

Precedence: null PK → duplicate PK → orphan trust → unmapped specialty → weeks unparseable/negative/out-of-range → referral unparseable/in-future. Each has a unit test that injects the failure and asserts the reason. See the decision tree in pipeline_explainer.html.

L3 · Incremental / CDC / SCD2

@incremental processes only new rows. We ship: append + watermark + snapshot reference lookups; a CDC change feed (INSERT/UPDATE/DELETE by comparing to the previous output); SCD Type 2 status history with effective dating; and windowed “top-5 longest waiters per trust”. The delta logic is in tested lib/scd.py. Diagram: pipeline_explainer.html.

L4 · Performance & cost — right engine for the job

The data is small, so the whole medallion runs on lightweight Polars/DuckDB single-node (cheap). problems/perf.py is one Spark transform that demonstrates AQE, broadcast join, salting the hot TR005 key, caching, column pruning, partitioned + bucketed writes, compaction — the techniques you reach for at scale. problems/cost.py pins @lightweight(1 core / 2 GB). Rule of thumb: Spark only when a distributed shuffle is genuinely needed.

L5 · Ontology, app, governance (PhD)

Ontology

Pathway and Trust object types, a many-to-one link, RAG conditional formatting, two edit-only properties, and a Triage Pathway action that writes them without touching source data. The Pathway is backed by the PII-free rtt_patient_pseudonymised dataset — the NHS number never enters the object layer.

Security model

  • In-pipeline: SHA-256 pseudonymise + drop nhs_number (a build-failing post-condition guards it).
  • Markings: apply “NHS Patient PII” to datasets that still carry nhs_number (raw/typed/clean/minimised/metrics/rejects). Markings propagate downstream automatically.
  • Restricted Views: row-level access by region. Property security: column-level. Encrypted secrets: in Data Connection.
  • Audit: SAE log + recon + action edit history + immutable transactions.

OSDK internals

Developer Console generates a typed npm SDK from the Ontology. A React app imports the object types + actions and talks to Foundry over OAuth. Real-time subscriptions push object changes to the UI. The app/rtt_command_centre.html here is the “instant” version (double-click to run); the deployment runbook productionises it.

Disaster recovery

Every build is an addressable transaction; roll back by re-pointing, or rebuild deterministically from seed (idempotent). Branches give point-in-time snapshots.

A · Build & schedule the pipeline (UI)

  1. Open the project → /code/rtt-transforms → Code Repositories. Confirm the latest commit’s Checks are green.
  2. Open a Gold dataset (e.g. rtt_ptl) → top-right Build. Foundry builds it and all required inputs in dependency order.
  3. To automate: on rtt_ptl (and rtt_trust_specialty_perf) open the ··· menu → Schedules → New schedule. Set trigger Time 06:00, scope Build required inputs. Save + enable.
  4. For event triggers/SLAs use Automate: New automation → trigger “new transaction on trust_fdp_rtt_pathways_raw” → effect “build rtt_ptl” (+ notify on freshness). See docs/SPECS.md#automation.
No cron, no Airflow — scheduling and orchestration are native.

B · Publish the ontology (UI)

  1. The feature branch already has an open Proposal (PR): “RTT-Programme — The 50 Problems, Solved”.
  2. Open the proposal → review the ontology changes (Trust, Pathway, link, Triage action) and code diff.
  3. Resolve any checks, then Merge / Deploy to main. The object types and action become live on the default ontology.
  4. Open Ontology Manager → verify Pathway shows 15 properties, the Pathway→Trust link and the Triage action. Click Sync if a datasource just rebuilt.

C · Apply PII markings (UI)

  1. In Control Panel → Markings, create/choose marking “NHS Patient PII”.
  2. For each dataset that still carries nhs_number (raw, typed, clean, minimised, metrics, rejects): open it → ··· → Manage → Markings → Add marking.
  3. Markings propagate to downstream outputs automatically. The Ontology backing (rtt_patient_pseudonymised) is PII-free and needs none.
  4. Verify: as a user without the marking, opening rtt_pathways_clean is denied, but the Pathway object still works.

D · Deploy the React app as a real OSDK app (UI)

The single-file app/rtt_command_centre.html is the instant demo. To productionise it against the live Ontology, follow the OSDK path (grounded in Foundry docs).

  1. Developer Console → + New application → Client-facing application.
  2. Select Ontology resources: object types RttPathway, RttTrust; action rtt-triage-pathway; the Pathway→Trust link. (The Ontology binding can’t be changed later.)
  3. Generate SDK: “Yes, generate an Ontology SDK” → Generate first version. Regenerate whenever the Ontology shape changes.
  4. Redirect URL: set http://localhost:8080/auth/callback for dev. In Control Panel → CORS allow http://localhost:8080 (do this before local dev or calls fail silently).
  5. Create code repository from Developer Console — it bootstraps React + TypeScript + Vite + OAuth with the OSDK pre-wired.
  6. Open in VS Code (in-platform) or Work locally (clone + FOUNDRY_TOKEN). Set env: VITE_FOUNDRY_CLIENT_ID, VITE_FOUNDRY_REDIRECT_URL, VITE_FOUNDRY_API_URL, VITE_FOUNDRY_ONTOLOGY_RID.
  7. Port the UI: reuse the components from app/rtt_command_centre.html; replace the FoundryDataSource with the typed client: 
    const page = await client(RttPathway).fetchPage({ $pageSize: 200 });
await client(rttTriagePathway).applyAction({ pathway: id, reviewStatus, triageNote });
  8. Run npm install && npm run dev. Then npm run lint && npm run test && npm run build.
  9. Cut a release: git tag 1.0.0 && git push origin tag 1.0.0 (or via Code Repositories UI). Wait for checks.
  10. Deploy: Developer Console → Website hosting → upload dist/ (or @osdk/cli). URL: <subdomain>.<enrollment>.palantirfoundry.com.
  11. Share: Developer Console → Sharing → Share hosted website (Viewer = website only).
Gotchas (from the docs): configure CORS before local dev; regenerate the SDK on any Ontology change; the default CSP blocks non-Foundry URLs silently (check F12); the redirect URL must match in .env, index.html and Developer Console; hosting is static assets only (no server code — use Functions for that).

Alternative (fastest): keep this UI as a Workshop module instead — see docs/SPECS.md#workshop. Trade-off table is in the OSDK docs (control vs speed).

E · Open the HTML files (UI)

  1. Open the repo → Files tab → docs/ or app/.
  2. Select a file (e.g. app/rtt_command_centre.html) → ··· → Download.
  3. Double-click the file to open in your browser (diagrams/React load from CDN, so first open needs internet).
  4. Or serve locally: in the folder run python -m http.server and browse http://localhost:8000/.
  5. Keep them beside your Foundry_Learning_Journey.html for the full package. See docs/HOW_TO_OPEN.md.

Operate it — Clare’s weekly runbook

  1. Open the RTT Command Centre (app or hosted OSDK app).
  2. Check the KPI row: is % within 18 weeks above 92%? How many 52/65-week breaches?
  3. Filter to RED + Active, sort by Weeks desc — the longest waiters first.
  4. Open a pathway (row → drawer) → Triage: pick Validated / Needs escalation / Data query / Removed in error + a note.
  5. Use Bulk triage for a batch; Export CSV for the weekly return; check the Audit tab for what changed.

Extend it

Add a new data-quality rule

  1. Add a branch to lib/dq_rules.add_reject_reason + a case in test_dq_rules.py.
  2. Commit → CI runs pytest → build rtt_pathways_clean. Recon still balances.

Add a new object type / property

  1. Add the column in the backing transform; build the dataset.
  2. In Ontology Manager add the property/object → map to the column → Sync.
  3. Regenerate the OSDK → rebuild the app.

QuarantineWhere bad rows go, tagged with a reject_reason (never dropped).

ReconReconciliation totals proving no silent row loss.

FAQ

Where is the actual data?

In the datasets under /RTT-Programme — RIDs in the Reference section. Query them via the SQL console or the app’s Connect tab.

Why is % within 18 weeks low?

The seeded distribution deliberately includes many long waiters so breaches and RAG are visible. Real data will differ.

Why only Trust + Pathway objects, not Specialty/Patient?

The tenant Ontology is at its 60 object-type cap; Specialty/Patient are Pathway properties instead. Logic is unaffected.

Does the React app change the real data?

By default no — it’s in-memory (persisted to your browser). In Connect / live mode, Triage calls the real action; other writes need matching action types.

How do I recover from a bad build?

Datasets are immutable transactions — roll back to a prior transaction, or rebuild from seed (deterministic).
