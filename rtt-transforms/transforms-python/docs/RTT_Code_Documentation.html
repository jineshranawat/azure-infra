📋 Project Overview

What is the RTT Programme?

The Referral-to-Treatment (RTT) Programme is an NHS England initiative that tracks patient waiting times from the point of GP referral to the start of treatment. This codebase implements a complete data platform that ingests, cleanses, validates, and transforms RTT pathway data into actionable operational intelligence.

Real-World Analogy: The Hospital Traffic Controller

Imagine you're managing traffic flow at a busy airport. Every plane (patient pathway) has:

  • An arrival time (referral date)
  • A designated runway/terminal (specialty like Cardiology, Orthopaedics)
  • A target departure time (18-week treatment target)
  • Status tracking (Active = waiting, Discharged = treated)

Our system is like an air traffic control tower - it monitors every patient journey, flags those at risk of "missing their slot" (breaching 18 weeks), and gives operators a clear dashboard to prioritise who needs attention first.

Key Business Objectives

Objective Description Success Metric
18-Week Compliance 92% of patients should start treatment within 18 weeks of referral Constitutional standard monitoring
Long Waiter Elimination Identify and prioritise 52+ week and 65+ week breaches Zero tolerance for long waiters
Data Quality Clean, validated data with full audit trail Quarantine & reconciliation
Operational Visibility Real-time Patient Tracking List for operations managers Clare's RTT Command Centre

🏢 Enterprise Pattern: Medallion Architecture

Why layers matter: In enterprise data platforms, data flows through quality gates. Each layer adds value:

  • Bronze (Raw): Preserve original data exactly as received - never lose source truth
  • Silver (Cleansed): Apply business rules, validate, enrich - make data trustworthy
  • Gold (Marts): Pre-aggregate for specific use cases - make data consumable

Key Palantir Foundry Concepts Used

Concept What It Does Where Used
@transform Defines a data transformation with explicit inputs/outputs Every transform file
Input() / Output() Declares dataset dependencies - Foundry tracks lineage automatically All decorators
LightweightInput Uses single-node compute (Polars/Pandas) instead of Spark - faster for small data Most transforms
Check() with expectations Built-in data quality assertions that FAIL or WARN builds Output datasets
paths.py Single source of truth for all dataset paths - change once, update everywhere Imported by all transforms

🥇 Medallion Architecture Layers

🥉
Bronze Layer

File: raw_ingest.py

Purpose: Cast string columns to proper types. Flag parse failures but keep ALL rows.

Principle: Never drop data at Bronze - just add metadata about quality issues.

🥈
Silver Layer

Files: clean_silver.py, sae_minimise.py, metrics.py

Purpose: Validate, canonicalise, quarantine bad rows, remove PII, add business metrics.

Principle: Bad rows go to quarantine with reasons - never silently dropped.

🥇
Gold Layer

File: marts.py

Purpose: Pre-aggregated tables optimised for specific users (e.g., PTL for Clare).

Principle: Fast reads for dashboards - computation done once upstream.

Real-World Analogy: Restaurant Kitchen Workflow

Think of data layers like a professional kitchen:

  • Bronze (Receiving Bay): Ingredients arrive in boxes. You inspect, weigh, and label them but don't throw anything away - even the bruised tomatoes get logged.
  • Silver (Prep Kitchen): Chefs wash, chop, and prepare ingredients. Bad items go in a separate "reject bin" with labels explaining why. Clean ingredients go to the cook line.
  • Gold (Plated Dishes): Final dishes are assembled for specific customers. The Beef Wellington is pre-sliced, the salad is dressed - ready to serve instantly.

1. seed.py - Source Data Generation

📖 Purpose

Creates deterministic, reproducible source data so the entire pipeline is self-contained. In production, these datasets would come from Data Connection syncs (external systems).

Key Functions:

  • seed_provider_reference() - Creates the 5 NHS Trust reference records
  • seed_specialty_reference() - Creates the 10 medical specialty codes
  • seed_sae_column_rules() - Metadata-driven PII column removal rules
  • seed_rtt_pathways_raw() - 1,215 rows: 25 verbatim + 1,175 generated + 15 intentionally dirty
# The 15 dirty rows test every DQ rule: _DIRTY_PATHWAYS = [ # Dirty specialty variants -> canonicalised in clean (Problem 40) ("PWD001", "TR001", "T&O", ...), # "T&O" → "Trauma and Orthopaedics" ("PWD002", "TR002", "gen surg", ...), # "gen surg" → "General Surgery" # Blank specialty -> quarantine (Problem 8/40) ("PWD006", "TR001", "", ...), # Cannot map blank → reject # Orphan trust code -> quarantine (Problem 34) ("PWD007", "TR999", "Cardiology", ...), # TR999 doesn't exist → reject # Negative weeks -> quarantine (Problem 35) ("PWD009", "TR002", "Neurology", "-5", ...), # -5 weeks is invalid → reject ]
⚠️ Why Inject Dirty Data?

Real-world data is NEVER perfect. By intentionally including dirty rows, we prove that:

  • Our DQ rules catch every known failure mode
  • Bad rows are quarantined (not silently dropped)
  • We can trace exactly why each row was rejected

2. raw_ingest.py - Bronze Layer

📖 Purpose

Type-cast the all-string CSV-landed data into proper types (dates, integers). Flag rows where parsing fails but NEVER drop them.

@transform.using( src=Input(paths.RTT_PATHWAYS_RAW), out=Output( paths.RTT_PATHWAYS_TYPED, checks=[ Check(E.col("pathway_id").non_null(), "raw: pathway_id present", on_error="WARN"), ], ), ) def compute(src: LightweightInput, out: LightweightOutput) -> None: df = src.polars() df = df.with_columns([ # Keep original string values for debugging pl.col("referral_date").alias("referral_date_str"), # Parse using tested helper functions pl.col("referral_date").map_elements(C.parse_date, return_dtype=pl.Date), pl.col("weeks_waited").map_elements(C.to_int, return_dtype=pl.Int64), ]).with_columns([ # Flag parse failures (NULL after parsing but non-blank original) (pl.col("weeks_waited").is_null() & pl.col("weeks_waited_str").is_not_null() & (pl.col("weeks_waited_str").str.strip_chars() != "")).alias("weeks_parse_failed"), ]) out.write_table(df)

3. clean_silver.py - Silver Layer (Main Cleansing)

📖 Purpose

This is the HEART of data quality. It canonicalises specialties, validates every row against business rules, routes bad rows to quarantine with reasons, and proves clean + rejects = input (no silent loss).

Three Outputs:

Output Dataset Purpose Row Count (Example)
rtt_pathways_clean Valid, trustworthy rows ready for downstream 1,205 ✅
rtt_pathways_rejects Invalid rows with reject_reason column 10 ❌
recon_control_totals Reconciliation: typed_count = clean + reject Proves 1,215 = 1,205 + 10
# Quarantine policy lives in ONE tested place (lib.dq_rules) df = dq_rules.add_reject_reason(df, valid_trusts, SNAPSHOT, MAX_WEEKS) # Split clean vs rejects clean_df = df.filter(pl.col("reject_reason").is_null()) rejects_df = df.filter(pl.col("reject_reason").is_not_null()) # PROVE no silent data loss n_in, n_clean, n_rej = df.height, clean_df.height, rejects_df.height recon_df = pl.DataFrame({ "metric": ["typed_count", "clean_count", "reject_count", "reconciled"], "value": [n_in, n_clean, n_rej, int(n_clean + n_rej == n_in)], })
✅ Data Expectations (Quality Gates)

FAIL expectations prevent bad data from ever reaching downstream consumers:

  • E.primary_key("pathway_id") - Every row must have unique, non-null PK
  • E.col("weeks_waited").gte(0).lte(520) - Valid range (0-10 years)
  • E.col("specialty_code").non_null() - Every specialty must be mapped

4. sae_minimise.py - IG Data Minimisation

📖 Purpose

SAE = Sufficient, Accurate, Exact - A legal/governance principle that you should only hold the minimum data necessary. This transform removes PII columns (sex, age_at_referral, source_load_ts) before data leaves Silver.

Key Feature: Metadata-Driven

The columns to drop are NOT hard-coded. They're read from the sae_column_rules reference table. IG can update the policy without a code change.

# Read drop-list from reference table drop_cols = S.columns_to_drop(rules_df.to_dicts(), SAE_DATASET_NAME) # Apply minimisation kept, dropped = S.apply_minimisation(df.columns, drop_present) minimised_df = df.select(kept) # HARD POST-CONDITION: banned columns must not survive if not S.assert_minimised(minimised_df.columns, _MUST_BE_ABSENT): raise ValueError(f"SAE minimisation failed!") # Fails the build # Audit log records what was removed and when audit_df = rules_df.with_columns([ pl.lit(applied_ts).alias("applied_ts"), pl.col("column_name").is_in(dropped).alias("column_dropped"), ])

📚 Library Functions - The Building Blocks

🏢 Enterprise Pattern: Separation of Concerns

Why a separate /lib folder? Business logic lives in pure Python functions that:

  • Are engine-agnostic - work with Polars, Pandas, or plain Python
  • Are independently testable - pytest runs without Spark/Foundry
  • Follow Single Responsibility - each module does one thing well
  • Enable reuse - same functions used in transforms AND unit tests

lib/canonicalise.py - Text Normalisation & Parsing

Function: canonical_specialty(value)

Maps dirty free-text specialty variants to clean reference names.

# Synonym dictionary (dirty → clean) _SPECIALTY_SYNONYMS = { "t and o": "Trauma and Orthopaedics", "t o": "Trauma and Orthopaedics", "ortho": "Trauma and Orthopaedics", "gen surg": "General Surgery", "ent": "Ear Nose and Throat", "cardio": "Cardiology", ... } def canonical_specialty(value: Optional[str]) -> Optional[str]: """Map a dirty free-text specialty to a canonical name, else None.""" key = normalise_text(value) # lowercase, strip, expand & if key is None: return None return _SPECIALTY_SYNONYMS.get(key)
Real-World Analogy: Spell-Check for Hospital Departments

Think of this like autocorrect for department names. When someone types "T&O" or "ortho" or "Trauma & Orthopaedics", we recognise they all mean the same thing and standardise to the official name: "Trauma and Orthopaedics".

Function: parse_date(value)

Parses dates from multiple formats (YYYY-MM-DD, DD/MM/YYYY, ISO timestamps).

_DATE_FORMATS = ("%Y-%m-%d", "%d/%m/%Y", "%d-%m-%Y", "%Y/%m/%d", "%m/%d/%Y") def parse_date(value) -> Optional[dt.date]: """Parse a date from several known formats; None if unparseable.""" # Handle datetime objects directly if isinstance(value, dt.datetime): return value.date() # Try each format in order for fmt in _DATE_FORMATS: try: return dt.datetime.strptime(text, fmt).date() except ValueError: continue return None # Unparseable → will trigger quarantine downstream

lib/dq_rules.py - The Quarantine Policy

⚠️ Critical Design: Single Source of Truth

ALL quarantine logic lives in ONE function: add_reject_reason(). This means:

  • The exact same logic runs in transforms AND unit tests
  • When we fix a bug, it's fixed everywhere
  • We can test every reject reason with crafted data frames
def add_reject_reason(df, valid_trusts, snapshot, max_weeks) -> pl.DataFrame: """Add reject_reason column: None = valid, else = first rule violated.""" # Mark duplicate primary keys (keep first occurrence) df = df.with_columns( (~pl.col("pathway_id").is_first_distinct()).alias("_is_dup_pk") ) # Cascading WHEN/THEN - order = precedence reason = ( pl.when(pl.col("pathway_id").is_null()) .then(pl.lit("null_pathway_id")) # Problem 8/42 .when(pl.col("_is_dup_pk")) .then(pl.lit("duplicate_pathway_id")) # Problem 1/42 .when(~pl.col("trust_code").is_in(valid_trusts)) .then(pl.lit("orphan_trust_code")) # Problem 34 .when(pl.col("specialty_code").is_null()) .then(pl.lit("unmapped_specialty")) # Problem 40 .when(pl.col("weeks_waited") < 0) .then(pl.lit("weeks_waited_negative")) # Problem 35 .when(pl.col("weeks_waited") > max_weeks) .then(pl.lit("weeks_waited_out_of_range"))# Problem 35 .when(pl.col("referral_date") > snapshot) .then(pl.lit("referral_date_in_future")) # Problem 41 .otherwise(pl.lit(None)) ) return df.with_columns(reason.alias("reject_reason"))

🎓 Key Concepts Explained

Concept 1: Lightweight Transforms

📖 What is it?

@transform.using() with LightweightInput/Output opts out of Apache Spark and uses single-node compute (Polars/Pandas). This is faster and cheaper for datasets under ~10 million rows.

Real-World Analogy: Bicycle vs. Semi-Truck

Spark is like a fleet of semi-trucks - great for moving mountains of data across a warehouse. But for 1,200 rows? That's like hiring 100 trucks to deliver a pizza. Lightweight transforms are like a bicycle - nimble, fast, and perfectly suited for the job.

# Lightweight transform (single-node, Polars) @transform.using( src=Input(paths.RTT_PATHWAYS_RAW), out=Output(paths.RTT_PATHWAYS_TYPED), ) def compute(src: LightweightInput, out: LightweightOutput) -> None: df = src.polars() # Returns a Polars DataFrame (NOT Spark) # ... process with Polars ... out.write_table(df)

Concept 2: Polars vs PySpark

Feature Polars PySpark
Execution Single-node, in-memory Distributed across cluster
Best for < 10M rows > 10M rows, joins of large tables
Startup time Instant 30+ seconds (cluster provisioning)
Syntax feel Modern, expressive, chainable SQL-like, verbose

Concept 3: Data Lineage & Dependency Tracking

🏢 Enterprise Pattern: Automatic Lineage

When you declare Input("path/to/dataset"), Foundry automatically:

  • Tracks that your transform depends on that dataset
  • Rebuilds downstream when upstream changes
  • Visualises the full data lineage graph
  • Enables impact analysis ("what breaks if I change X?")

Concept 4: Referential Integrity

📖 What is it?

Referential integrity means foreign keys (FKs) must exist in their parent table. If trust_code = "TR999" but TR999 isn't in provider_reference, that's an orphan record - it references something that doesn't exist.

# In clean_silver.py - check FK exists valid_trusts = providers.polars()["trust_code"].to_list() # ["TR001", "TR002", ...] # In dq_rules.py - quarantine orphans .when(~pl.col("trust_code").is_in(valid_trusts)) .then(pl.lit("orphan_trust_code"))

Concept 5: Idempotent & Deterministic Transforms

📖 What does this mean?
  • Idempotent: Running the same transform twice produces the same output
  • Deterministic: Given the same inputs, output is always identical

This is why seed.py uses random.Random(42) - the seed ensures "random" data is reproducible across runs.
