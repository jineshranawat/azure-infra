The Palantir FDE Playbook

One page that teaches every concept used to build "The 50 Problems, Solved" reference implementation — and the exact step-by-step pathway so any senior engineer can rebuild it in their own project. Concepts are taught as: Concept → Why → How (code / UI) → RTT example → Do it in your project.

Who

Senior FDEs who want the full Foundry + AIP surface applied to one coherent, tested, production-grade build.

How to read

Top-to-bottom is a build order. Use the left rail to jump. Tick the checklist in §20 as you go (saved in your browser).

Golden rule

Every design choice traces to a constraint: legal/PII, performance, cost, or user need. No castles in the air. Executable + tested or it didn’t happen.

0 · Vocabulary you must own

Dataset / Transaction

A versioned table. Every build is an immutable transaction → time-travel + rollback for free.

Transform

Code (Python/SQL/Java) turning inputs → outputs. Lightweight (Polars/DuckDB, single node) or Spark (distributed).

Data Expectation / Check

Assertion embedded in a transform. FAIL blocks the build; WARN signals. Publishes to Data Health.

Ontology object / link / action

Rows→objects, joins→links, permitted mutations→actions (audited).

Function

Server-side logic (TS v1/v2, Python, AIP Logic). Powers computed properties, function-backed actions/columns.

OSDK

Typed SDK generated from the Ontology so external React apps read objects & run actions.

Marking / Restricted View

Marking = access control that propagates downstream. RV = row-level policy over a dataset.

Branch / Proposal

Isolated workspace; merge via a Proposal (PR) after checks. Global branches span code + ontology.

1 · Project structure & branching

Concept

Keep logic (repos) separate from data (datasets/objects) so security propagates cleanly. Work on short-lived branches; merge to master via a proposal after CI is green.

RTT layout

/RTT-Programme
  /reference   provider_reference, specialty_reference, sae_column_rules
  /raw         trust_fdp_rtt_pathways_raw            (Bronze)
  /clean       typed, clean, minimised, metrics + incremental (Silver)
  /marts       trust_specialty_perf, ptl, perf_*, cost_*  (Gold)
  /quarantine  rejects, schema_drift_report
  /audit       recon_control_totals, sae_audit_log, freshness_report
  /ontology-backing  patient_pseudonymised (PII-free)
  /code/rtt-transforms  (the Python repo)

Do it in your project

  1. Create a Project under your namespace; add medallion folders (/raw /clean /marts /quarantine /audit /reference /ontology-backing /code).
  2. Create a Python transforms code repository in /code.
  3. Cut a feature branch: ai-fde/<you>/<feature> (global branch if the change spans ontology + code).
  4. Every commit → CI runs. Open a Proposal when done; merge to master when green.

2 · Data Connection & ingestion

Concept & why

Bring source data in via a connector + sync. Batch → datasets; streaming/CDC → streams; media → media sets. Credentials live in encrypted secrets, never code. Configure retry + throttle on the sync (Problem 17).

RTT example

In this reference build the 4 sources are seeded deterministically from a transform (self-contained + replayable, Problem 19) instead of a live connector — but in production you’d point a JDBC/S3 connector at the trust extract with an incremental high-water on source_load_ts.

Do it in your project

  1. Data Connection → add a Source (JDBC/S3/REST/…); store creds as a secret; set an egress policy if needed.
  2. Create a batch sync (incremental, high-water column) or streaming/CDC sync; set maxRetries + backoff + throttle.
  3. Land into /raw as an all-string Bronze table so typing/validation happens in-pipeline.

3 · Datasets & the transaction model

Datasets are immutable-transaction tables. This gives you disaster recovery (Problem 50): roll back to a prior transaction, or rebuild deterministically from the seed. Branches give point-in-time snapshots. Schemas are inferred/declared; prefer explicit types at the typing stage.

4 · Code repository & transform types

Repo layout (tested + reusable)

transforms-python/src/myproject/
  paths.py           # single source of truth for dataset paths
  lib/               # pure, unit-tested helpers (engine-agnostic)
  datasets/          # medallion stages (seed, raw_ingest, clean_silver, ...)
    problems/        # one module per category (dq, perf, incremental, security, cost)
src/test/            # pytest mirroring lib/ (positive + negative)

Decorators you will use

DecoratorEngineWhen
@transform.using(...)Lightweight (Polars)Small/medium data (default). Inputs LightweightInput.polars().
@transform.spark.using(ctx, ...)SparkGenuine distributed shuffle. .dataframe() / .write_dataframe(partition_cols, bucket_cols,…).
@lightweight(cpu_cores, memory_gb) + @transformLightweight, pinned sizeRight-size a small job (cost).
@incremental(v2_semantics=True, snapshot_inputs=[...])either (goes above @transform…)Process only new rows; read modes added/current/previous.
@configure(profile=[...])Spark profileRight-sized executors / AQE.

Principle

Put logic in lib/ as pure functions (deterministic, testable), then call them from transforms. The unit test that proves the function also proves the pipeline column.

5 · The medallion build (Bronze → Silver → Gold)

raw→raw_ingest (type)→typed→clean_silver (canonicalise+quarantine)→clean +rejects+recon
clean→sae_minimise (IG)→minimised→metrics→metrics→marts→PTL / perf
Bronze — typed ingest (Problem 6, 10): reuse tested parsers
@transform.using(src=Input(paths.RTT_PATHWAYS_RAW), out=Output(paths.RTT_PATHWAYS_TYPED,
    checks=[Check(E.col("pathway_id").non_null(), "raw pk present", on_error="WARN")]))
def compute(src, out):
    df = src.polars().with_columns([
      pl.col("weeks_waited").map_elements(C.to_int, return_dtype=pl.Int64).alias("weeks_waited"),
      pl.col("referral_date").map_elements(C.parse_date, return_dtype=pl.Date).alias("referral_date"),
    ])
    out.write_table(df)   # bad casts -> null + flagged; nothing dropped in Bronze
Silver — canonicalise + quarantine (Problems 1,8,34,35,40,41,42) with recon
# lib/dq_rules.py  (one tested place for the whole quarantine policy)
reason = (pl.when(pk_null_or_blank).then(pl.lit("null_pathway_id"))
  .when(is_dup_pk).then(pl.lit("duplicate_pathway_id"))
  .when(~trust_in_ref).then(pl.lit("orphan_trust_code"))
  .when(specialty_unmapped).then(pl.lit("unmapped_specialty"))
  .when(weeks_null).then(pl.lit("weeks_waited_unparseable"))
  .when(weeks_lt_0).then(pl.lit("weeks_waited_negative"))
  .when(weeks_gt_max).then(pl.lit("weeks_waited_out_of_range"))
  .when(referral_null).then(pl.lit("referral_date_unparseable"))
  .when(referral_future).then(pl.lit("referral_date_in_future"))
  .otherwise(pl.lit(None)))
clean   = df.filter(reason.is_null())
rejects = df.filter(reason.is_not_null())   # /quarantine + reject_reason
# recon proves: typed_count == clean_count + reject_count  (no silent loss)
SAE minimisation (Problems 29,31) — metadata-driven, build-failing guard
drop = sae_minimiser.columns_to_drop(rules.to_dicts(), "rtt_pathways")  # sex, age, source_load_ts
minimised = clean.select([c for c in clean.columns if c not in drop])
assert not (set(minimised.columns) & {"sex","age_at_referral","source_load_ts"}), "banned column leaked"
Gold — metrics + marts (PTL for Clare, 92% standard)
# metrics: is_breach_18w, is_52w_breach, is_65w_breach, wait_band, rag_status
# marts: group by trust x specialty -> pct_within_18w, meets 92% standard; PTL = active pathways, longest first

6 · Data Expectations, pytest & CI

FAIL vs WARN — a deliberate choice

FAIL anything that would corrupt keys/joins/metrics (PK, range, ref-integrity, schema contract). WARN quality signals (raw nulls, freshness, unexpected columns). Bad rows are quarantined, so the FAIL checks on clean stay green because the policy works.

from myproject.lib import rtt_metrics as M
def test_wait_band():
    assert M.wait_band(18)=="0-18" and M.wait_band(65)=="65+"
    assert M.wait_band(-1) is None            # negative case: invalid -> no band
def test_is_breach():
    assert M.is_breach(19) is True and M.is_breach(18) is False
  1. Enable the pytest plugin in build.gradle: apply plugin: 'com.palantir.transforms.lang.pytest-defaults'.
  2. Write pure helpers in lib/; mirror with tests in src/test/ (each rule gets a negative test).
  3. Embed Check(E…, on_error="FAIL"|"WARN") in transform Outputs.
  4. CI (ci/foundry-publish) runs pytest + validates transforms on every commit; merge only when green. Target < 10 min, trunk-based.

8 · Incremental & Streaming 2,3,14,15,18,19,20,21,36,37,44

  • @incremental (2) processes only new rows; watermark (3) on source_load_ts via read mode added.
  • CDC (14): compare current vs the output’s previous → INSERT/UPDATE/DELETE feed. (Guard the first build: previous is schemaless → treat as empty.)
  • Dedup latest-wins (15) + late/out-of-order (20): keep max event-ts per key.
  • SCD Type 2 (18): accumulate snapshots (snapshot_inputs) then effective-date into valid_from/valid_to/is_current.
  • Windowing (21): rank longest waiters per trust. Idempotent replay/backfill (19,44): deterministic seed + bounded reprocessing.

Reach for Spark only when a distributed shuffle is warranted. One Spark transform demonstrates them all:

10 · Cost Optimization 26,27,28

Right-size (26) with @lightweight(cpu_cores=1, memory_gb=2) or a small Spark profile; warm pools / scale-to-zero (27) come from lightweight; pick the cheapest correct engine (28) — lightweight vs Spark. Rule: don’t pay for a cluster to sort 1,200 rows.

11 · Security & Governance 29,30,31,47,48

  • In-pipeline (29,31): SHA-256 pseudonymise nhs_number and drop it before the Ontology layer (build-failing post-condition guards it).
  • Markings (29): apply e.g. "NHS Patient PII" to every dataset still carrying nhs_number; it propagates downstream automatically.
  • Restricted Views (30): row-level policy (e.g. by region). Property security (31): column-level. Encrypted secrets (47): Data Connection.
  • Audit (48): SAE log + recon + Action edit history + immutable transactions.

UI steps (Markings)

  1. Control Panel → Markings → create/choose the marking.
  2. Dataset → ··· → Manage → Markings → Add. Verify a user without it is denied.

13 · Automation & Orchestration 7,16,17,38,39

No cron/Airflow. Schedules build the graph (7) in dependency order (39). Automate event/condition triggers (16) & SLA alerts (38). Connector retry/throttle (17) on the sync.

  1. Dataset (e.g. PTL) → ··· → Schedules → New → Time trigger, "build required inputs".
  2. Automate → New automation → trigger "new transaction on raw" → effect "build PTL"; add a freshness/SLA notification.

14 · Ontology — from tables to an operational app

Concept

Object types (rows), properties (columns, typed), link types (joins, cardinality), Actions (audited mutations), Functions (computed props / function-backed actions), Interfaces (polymorphism). Back objects on a PII-free dataset.

Trust1—<Pathway·Action: Triage Pathway

UI steps

  1. Ontology Manager → New object type → pick backing dataset → set primary key → map properties (match column types: Int64→long, Date→date, bool→boolean).
  2. Add a link type (many-to-one via the FK property). Add conditional formatting (RAG traffic-lights).
  3. Enable edits + add edit-only properties (e.g. review_status, triage_note).
  4. Create an Action (modifyObject) with allowed-value parameters → writes edit-only props without touching source data.
Gotcha: ontologies have an object-type cap (e.g. 60). If near it, model extra entities as properties rather than new objects (we folded Specialty/Patient into Pathway).

15 · Workshop (no-code app)

Fastest operational UI. Build the RTT Command Centre: KPI header (% within 18w vs 92%, 52/65-week counts), a PTL Object Table on Pathway (RAG formatting, filters), a detail panel with the Triage Pathway action button, and a Trust drill-down. Widgets + variables + events wire it together. Choose Workshop for speed; OSDK when you need full control / Git / tests.

16 · OSDK React app (full control)

UI steps (Developer Console)

  1. Developer Console → + New application → Client-facing; select object types + actions; Generate SDK.
  2. Set redirect URL http://localhost:8080/auth/callback; add that origin to CORS (Control Panel) before local dev.
  3. Create the bootstrapped code repository (React + TS + Vite + OAuth) → open in VS Code / Work locally; set the VITE_FOUNDRY_* env vars.
  4. Query + act with the typed client:
import { createClient } from "@osdk/client";
const page = await client(RttPathway).fetchPage({ $pageSize: 200 });
await client(rttTriagePathway).applyAction({ pathway: id, reviewStatus, triageNote });
  1. npm run lint && test && build → git tag → Website hosting deploys dist/ → Share.
Gotchas: regenerate the SDK on any Ontology change; default CSP blocks non-Foundry URLs (check F12); hosting is static-only (server logic → Functions); redirect URL must match in .env, index.html, Developer Console. If your build environment has no internet, a CDN-based single-file React page will be blank — ship a bundled build (Vite) or a dependency-free vanilla page.

17 · AIP — controlled, human-in-the-loop

LLM steps must be constrained, never free-roaming on reportable data.

  • AIP Logic to standardise messy specialty free-text: constrained enum output (10 canonical names or UNMAPPED) + confidence gate; a human promotes suggestions. Never writes reportable fields directly.
  • Agent as a read-only triage assistant: object-set search over Pathway, drafts a note, but a human submits the audited Triage action.
  • Evals: golden-set test cases + evaluators to keep LLM outputs in spec.

18 · Branch → PR → merge → deploy

  1. Commit on the feature branch; CI green.
  2. Open a Proposal (global branch): review ontology + code diff.
  3. Merge/Deploy to main → object types + datasets deploy; dataset builds run on master.
  4. Apply the PII Markings; set a Schedule; verify lineage + Data Health.
Ontology write actions require the object types deployed/indexed on master — merge first, then test the action.

Pitfalls & glossary

Top pitfalls (learned the hard way)

  • Ontology cap: plan object types; model extras as properties.
  • Ontology writes need master: merge the proposal before testing actions.
  • OSDK offline: CDN React blanks with no internet → bundle (Vite) or ship dependency-free.
  • Incremental first build: reading a not-yet-built output’s previous throws → guard as empty.
  • Spark types: Polars Int64 → Foundry long (not integer) when mapping ontology properties.
  • Don’t drop rows silently: always quarantine + reconcile.
