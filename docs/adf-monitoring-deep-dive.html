0. Why ADF Monitoring is a key skill

Classroom weight: ~8–12 hours theory + forever in production

Authoring a pipeline is half the job. Defect investigation is the other half: a failing Copy, a Databricks 3204, a wrong folder path, a watermark that never advances — all surface first in Monitor. Enterprises hire for people who can open a failed run, read which activity failed, extract the error JSON, decide retry vs fix-and-redeploy, and prove green.

Analogy: Author = writing the restaurant recipe. Monitor = the CCTV + ticket printer in the kitchen — every order (pipeline run), every station (activity), every burnt dish (error), every “try again in 30s” (retry).

Class factory: adf-shared-qgr7mj · RG rg-shared-class1 · eastus
Open Studio: ADF Studio deep link → left rail Monitor.
# Deploy / refresh pipelines first if needed cd D:\azure .\release.cmd adf # or full SQL+ADF: .\deploy-shared-adf-lab.cmd # Trigger a known-good demo from CLI cd shared-adf-lab .\orchestrate.cmd --run-pipeline pl_01_bronze_copy

1. Three objects you must never confuse

~4 hours until this is muscle memory

ObjectWhat it isWhere in MonitorFinLedger example
Pipeline run One execution of a whole pipeline (GUID runId). Has overall status, start/end, parameters. Monitor → Pipeline runs One click Trigger now on pl_01_bronze_copy
Activity run One execution of one activity inside that pipeline (Copy, Notebook, If, ForEach iteration, …). Open a pipeline run → activity list / Gantt The Copy activity that wrote to bronze
Trigger run One fire of a schedule / tumbling / event trigger that started a pipeline run. Monitor → Trigger runs pl_trig_01_tumbling_window_bronze 
flowchart TD
  T[Trigger run - optional] -->|starts| P[Pipeline run - runId GUID]
  P --> A1[Activity run: Get Metadata]
  P --> A2[Activity run: If Condition]
  P --> A3[Activity run: Copy]
  P --> A4[Activity run: Databricks Notebook]
  A3 -->|On failure| E[Error JSON on activity]
  A3 -->|policy retry| A3r[Activity run attempt 2]
A Succeeded pipeline can still have skipped activities. A Failed pipeline always has at least one failed (or cancelled) activity that stopped the happy path — open that activity first, not the pipeline header alone.

2. Status lifecycle (pipeline + activity)

~3 hours + drill with live runs

StatusMeaningWhat you do
QueuedAccepted; waiting for IR / concurrency slotWait; check Integration Runtime health if stuck
InProgressActivities executingWatch Gantt; open long-running Copy / Notebook
SucceededPipeline completed happy pathVerify data landed (Portal storage / Databricks)
FailedUnhandled failure after retries exhaustedOpen failed activity → Error → playbook §9
Canceling / CancelledUser or API cancelledRe-trigger if intentional; else find who cancelled
TimedOutHit activity or pipeline timeoutIncrease timeout or fix hang (cluster, lock)

Activity vs pipeline: Pipeline status rolls up activity outcomes. With if / switch / foreach, some activities never run — that is not a failure.

3. Studio Monitor blade — exact click path

~6 hours guided lab

  1. Open ADF Studio for adf-shared-qgr7mj (deep link above).
  2. Left rail → Monitor (gauge icon).
  3. Pipeline runs — default last 24h. Filter by pipeline name (pl_01), status Failed, time range.
  4. Click a run row → detail: parameters, variables, duration, Activity runs list + Gantt.
  5. Click a failed activity → tabs: Input · Output · Error · (sometimes) User properties.
  6. Optional: Trigger runs, Integration runtimes, Data flow debug (if using mapping DFs).

What to screenshot for trainers

  • Pipeline run header (name, status, runId)
  • Failed activity name + Error message first line
  • Output JSON snippet (rows copied / notebook run URL)

What NOT to paste in chat

  • PATs / connection strings from linked services
  • Full secret values in activity Input

~10 hours until fluent

7. Retries — activity policy vs orchestrator rounds

~8 hours

7.1 Activity-level policy (inside the pipeline)

Most FinLedger activities ship with ActivityPolicy(retry=1, retry_interval_in_seconds=30) in shared-adf-lab/scripts/adf_pipelines.py (and siblings).

SettingMeaningClass default
retryExtra attempts after first failure1 → up to 2 tries total
retryIntervalInSecondsWait between attempts30
timeoutMax duration for the activityOften 0.01:00:00 (1h) on long steps

Retry = “the oven smoked — wait 30s and try that dish again” without rewriting the recipe.

In Monitor you may see multiple activity attempts. Pipeline fails only after policy retries are exhausted (unless you have On Failure paths that continue).

7.2 Orchestrator-level retry (CLI)

Different concept: re-run whole pipelines that failed in a batch:

cd D:\azure\shared-adf-lab .\orchestrate.cmd --run-all-until-success --max-rounds 3 # README §K — loops failed pipelines up to 3 rounds
flowchart TD
  Fail[Activity fails] --> Pol{retry count left?}
  Pol -->|yes| Wait[Wait retryInterval seconds]
  Wait --> Retry[Run activity again]
  Retry --> Fail
  Pol -->|no| PipeFail[Pipeline run Failed]
  PipeFail --> Human[Engineer reads Error]
  Human --> Fix[Fix code / data / RBAC]
  Fix --> Redeploy[release.cmd adf]
  Redeploy --> Rerun[Trigger now / orchestrate --run-pipeline]

7.3 When NOT to raise retry

  • Expression typos, wrong notebook path — will fail forever; fix definition.
  • 403 / RBAC — fix role assignment, don’t hammer retries.
  • Transient 429 / cluster spin-up — retries help; keep interval ≥ 30s.

9. Defect investigation playbook (use every time)

~15 hours drills — this is the core of the 100h practice

Print this

  1. Reproduce — note pipeline name, trigger type (Debug / Trigger now / CLI), approximate time UTC.
  2. Locate — Monitor → Pipeline runs → filter name + Failed.
  3. Identify failing activity — first red node on Gantt / list (not necessarily the last).
  4. Read Error — copy errorCode + first sentence of message.
  5. Read Input — confirm expressions resolved as you intended (paths, notebook, SQL).
  6. Classify — data missing · auth/RBAC · compute (Databricks cluster) · expression · timeout · dependency (child).
  7. Fix at source — storage data, RBAC, cluster, code in git → release.cmd adf or lab redeploy.
  8. Re-run — same pipeline; confirm Succeeded + Output rows / notebook OK.
  9. Document — one line in trainer notes: errorCode → root cause → fix (builds the catalog).
flowchart TD
  S[Symptom: pipeline Failed] --> M[Monitor: open run]
  M --> A[Find failed activity]
  A --> E[Read Error + errorCode]
  E --> I[Read Input - resolved values]
  I --> C{Classify}
  C -->|RBAC / 403| R[Fix role / firewall]
  C -->|Path / expression| X[Fix pipeline JSON in git]
  C -->|Databricks| D[Cluster / notebook / PAT]
  C -->|SQL| Q[Firewall / login / query]
  C -->|Child failed| Ch[Open child run - repeat]
  R --> RD[Redeploy if definition changed]
  X --> RD
  D --> RD
  Q --> RD
  Ch --> RD
  RD --> RR[Re-run pipeline]
  RR --> V{Succeeded?}
  V -->|yes| Done[Verify data]
  V -->|no| M

12. End-to-end monitoring workflows (diagrams)

12.1 Happy path — Trigger → Monitor → verify data

flowchart LR
  A[release.cmd adf] --> B[Factory has latest pipelines]
  B --> C[Trigger now pl_01_bronze_copy]
  C --> D[Monitor: Pipeline run InProgress]
  D --> E[Activity Copy Succeeded]
  E --> F[Pipeline Succeeded]
  F --> G[Portal: bronze container has file]

12.2 Failure path — minute-by-minute

flowchart TD
  T0[0:00 Trigger now] --> T1[0:01 Monitor shows InProgress]
  T1 --> T2[0:02 Activity fails - red]
  T2 --> T3[0:02-0:32 ActivityPolicy retry wait 30s]
  T3 --> T4[0:32 Second attempt fails]
  T4 --> T5[0:32 Pipeline Failed]
  T5 --> T6[Open Error tab - copy errorCode]
  T6 --> T7[Open Input - check path]
  T7 --> T8[Classify + fix in git / Azure]
  T8 --> T9[release.cmd adf if definition changed]
  T9 --> T10[Trigger now again - expect Succeeded]

12.3 Databricks notebook activity failure

flowchart LR
  P[pl_07 / pl_db_* run] --> N[Notebook activity Failed]
  N --> E[Error 3204 or notebook 404]
  E --> C{Which?}
  C -->|3204| CL[Start / fix cluster + PAT]
  C -->|404| NB[deploy-shared-lab.cmd notebooks]
  CL --> R[Re-run pipeline]
  NB --> R
