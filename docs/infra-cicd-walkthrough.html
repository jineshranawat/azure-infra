0. Prerequisites — unlock the toolbox (detail)

Theory: Before any cloud change, the developer machine must have a package manager (pip), authenticated Azure identity, and configuration (.env). Enterprises call this “agent / runner bootstrap” (Azure Pipelines Microsoft-hosted agent already has az + tools; here the learner laptop is the agent). Without bootstrap, every later phase fails with confusing auth or missing-module errors — so we separate Phase 0 on purpose.

Analogy: unlock the toolbox and check your badge at the restaurant gate before touching ovens.

# First time on a clean Windows PC (from repo root) .\orchestrate.cmd --install-cli # Edit .env in Notepad — must include at least: # AZURE_SUBSCRIPTION_ID=... # CLASS_OWNER_EMAIL=you@company.com (or OWNER_EMAIL=...) # DATABRICKS_HOST=https://adb-....azuredatabricks.net # DATABRICKS_TOKEN=... (for notebook deploys) # Optional SPN for Cost API / automation: # AZURE_TENANT_ID / AZURE_CLIENT_ID / AZURE_CLIENT_SECRET az login az account set --subscription a64c0dd2-3a31-4604-bde3-3d40c7d5e8be .\infra-walkthrough.cmd --phase 0

What Phase 0 does: ensures .venv, reminds you to az login, prints Python SDK status. Files: .env, requirements.txt, .venv/, infra-walkthrough.cmd.

Verify: terminal shows Azure CLI: OK and Python SDK: OK.

Theory: The shared estate is created once (or updated Incremental), then lab assets and orchestration are layered on. Running phases in order mirrors enterprise “landing zone → platform → workloads.” Each phase is idempotent: re-run after success is safe.

2. Incremental release paths — full detail (after git push)

Theory: CI/CD separates integrate (git) from deliver (deploy). Always check in first so the repo is the source of truth. Then choose the smallest deploy package — Microsoft’s guidance for ADF and Databricks is the same: promote only what changed; keep environments reproducible.

2a. Standard check-in (every change)

cd D:\azure git status git pull # ... edit builders / ADF scripts / docs ... git add -A git commit -m "Clear why + which guardrail" git push origin main git push class main

Never commit: .env, keys, docs/cost-dashboard-out/.

2b. Notebooks only → Databricks

Theory: Workspace import API overwrites the same notebook path. Re-release replaces content; it does not fork a duplicate. Use when only Day 8/9 / lab notebook sources changed. Does not rebuild SQL or re-deploy every ADF pipeline definition unnecessarily (though deploy-shared-lab may refresh shared assets).

.\release.cmd databricks # Under the hood: # day9\orchestrate.cmd --deploy # deploy-shared-lab.cmd → scripts\deploy_shared_lab.py

Verify: Databricks → /Shared/day9/ → open changed notebook → check modified time → Run all on a cluster.

2c. ADF pipelines only (skip SQL)

Theory: Enterprise ADF CI/CD publishes ARM and deploys to another factory. In class we redeploy pipelines/linked services in place on the shared factory with --skip-sql so the SQL server is not touched on every pipeline typo — that is blast-radius control (same idea as deploying app code without recreating the database).

.\release.cmd adf # Under the hood: # shared-adf-lab\orchestrate.cmd --skip-sql # → scripts\run_shared_adf.py --skip-sql # Optional smoke after deploy: shared-adf-lab\orchestrate.cmd --run-pipeline pl_01_bronze_copy

Verify: ADF Studio → Author → pipeline → Debug or Trigger now → Monitor.

2d. ADF + SQL (rare)

Theory: Use when SQL Bicep, firewall, login, or first-time database bootstrap changed. Recreating SQL often is slow and disruptive — hence “rare.” Matches enterprise rule: schema/infra changes go through a heavier pipeline than app config.

.\release.cmd adf-full # → deploy-shared-adf-lab.cmd (includes SQL path)

2e. Build + Databricks + ADF — no job (classroom default)

Theory: Coherent change-set when medallion notebooks and ADF governance pipelines must stay in sync. Skipping the job separates deploy from execute — enterprises often require a manual approval or scheduled trigger before production compute burns money. In class: deploy first, run job when ready.

.\release.cmd medallion-deploy # Equivalent: .\release-medallion-governance.cmd --skip-run

2f. Same + run medallion job (costs DBUs)

Theory: Continuous Deployment that also triggers a workload. Proves the release end-to-end but spends Databricks DBUs (and any ADF activity charges). Use deliberately after medallion-deploy when you want a cooked dinner.

.\release.cmd medallion # Equivalent: .\release-medallion-governance.cmd # Job helper: scripts\run_medallion_governance_job.py

2g. Verify checklist command

.\release.cmd verify # Then manually open: # Databricks /Shared/day9/ # ADF Studio → Monitor # Portal storage bronze/silver/gold/audit

2h. Release hub menu (see all options)

.\release.cmd .\release.cmd --help

Theory overview — concepts, enterprise pattern, then commands

Enterprises do not click Portal forever. They treat infrastructure, pipelines, and notebooks as code in git, then promote changes through environments with automated or scripted deploy. FinLedger teaches the same ideas on one shared classroom estate (dev/test style), using Windows one-liners instead of a full Azure DevOps org.

Terraform theory → students run these (same estate as Bicep)

Teach top-to-bottom. Each theory block has the exact Windows command students run next. Terraform does not call the .bicep file — both blueprints talk to ARM for the same house.

Desk twin: docs/BICEP-TERRAFORM-SHARED-ESTATE.md · Live hash name_hash=qgr7mj · Never teardown rg-shared-class1
Verified 19 Jul 2026: Terraform v1.15.8 → terraform validate Success → provision-shared-tf.cmd --plan-only = 14 to add, 0 change, 0 destroy (stsharedqgr7mj / kv-shared-qgr7mj / adf-shared-qgr7mj / dbw-shared-qgr7mj). Do not apply on the live shared RG without import — Bicep already owns it.

Classroom ladder — say the theory, then they run the block

Analogy: Bicep = Microsoft CAD; Terraform = HashiCorp AutoCAD. Same walls. Different drawing tool. ARM still pours the concrete.

T0 — Install the drawing tool (once per laptop)

Theory: Bicep rides inside Azure CLI. Terraform is a separate binary that downloads providers (plugins) for Azure, Entra ID, etc. Enterprises pin the binary + lock file so every agent builds the same plan. Without install, every later TF command fails with “terraform not found.”

# From any folder — one-time install winget install Hashicorp.Terraform --accept-source-agreements --accept-package-agreements # Close and reopen Command Prompt / PowerShell, then: terraform version # Expect: Terraform v1.x.x

Verify: terraform version prints a version. Files: WinGet PATH entry for Hashicorp.Terraform.

T1 — Auth + config (same gate as Bicep)

Theory: Terraform’s Azure provider uses your az login token when ARM_USE_CLI=true (our driver sets this). Same identity, same subscription, same .env owner email. IaC language changes; Azure identity does not.

cd D:\azure az login az account set --subscription a64c0dd2-3a31-4604-bde3-3d40c7d5e8be # .env must have CLASS_OWNER_EMAIL or OWNER_EMAIL (driver reads it) .\infra-walkthrough.cmd --phase 0

T2 — Open both blueprints side-by-side (teach, no Azure change)

Theory: Declarative IaC means you describe desired state, not a click path. Compare one resource (e.g. storage account) in Bicep vs HCL: same SKU, same region exception (eastus), same tags. Students see that TF is not “calling” Bicep — it is a second description of the same ARM types.

cd D:\azure # Open in editor (Cursor / VS Code / notepad) notepad infra\shared-eastus.bicep notepad infra\terraform\shared-eastus\main.tf notepad docs\BICEP-TERRAFORM-SHARED-ESTATE.md # Or list the twin folders dir infra\terraform\shared-eastus dir infra\terraform\shared-sql-westus

Point at in class: variable / locals / resource "azurerm_storage_account" ↔ Bicep param / var / Microsoft.Storage/storageAccounts.

T3 — init = download providers + lock file (Benefit: registry + pins)

Theory: terraform init reads required_providers, downloads signed azurerm / azuread binaries into .terraform/, and records exact versions in .terraform.lock.hcl (committed). Next machine gets the same plugins — reproducible builds. Bicep has no equivalent lock file for providers.

cd D:\azure\infra\terraform\shared-eastus terraform init -input=false # Look at the pin file we commit: type .terraform.lock.hcl | more

Verify: message Terraform has been successfully initialized. Do not commit .terraform/ folder (gitignored) — do commit .terraform.lock.hcl.

T4 — validate = syntax + provider schema (Benefit: HCL validation)

Theory: Catch typos and wrong argument names before talking to Azure. Our module uses azurerm ~> 3.117 (e.g. enable_rbac_authorization, not the 4.x name). validation blocks on variables (location must be eastus) fail fast here.

cd D:\azure\infra\terraform\shared-eastus terraform validate # Also validate the SQL twin: cd D:\azure\infra\terraform\shared-sql-westus terraform init -input=false terraform validate

Verify: Success! The configuration is valid.

T5 — plan = show create/change/destroy BEFORE Azure changes (Benefit: plan before apply)

Theory: This is Terraform’s killer feature vs click-ops and vs optional Bicep what-if. Plan answers: what will be added, changed, or destroyed? Students approve in their head; nothing is applied yet. Our Windows entry wraps plan with .env + subscription + principal + name_hash=qgr7mj.

cd D:\azure .\provision-shared-tf.cmd --plan-only # Same thing via walkthrough phase 1t (applies with --auto-approve — trainers: prefer --plan-only above in class) # .\infra-walkthrough.cmd --phase 1t

Verify: Plan ends with a summary like Plan: N to add, 0 to change, 0 to destroy and names stsharedqgr7mj, adf-shared-qgr7mj, … matching the live Bicep estate. Line Plan only — no changes applied means Azure was not mutated.

T6 — Why plan says “create” when Portal already has the resources (Benefit: state)

Theory: Empty local terraform.tfstate = Terraform thinks nothing exists. Azure may already have the RG from Bicep. Plan proposes creates → a blind apply would collide on names. State is Terraform’s memory. Bicep has no state file — Azure deployment history is different. Classroom rule: on the shared class RG, stay on plan-only unless the trainer runs import.

cd D:\azure # Safe classroom default — always: .\provision-shared-tf.cmd --plan-only # Greenfield ONLY (new names) — empty hash creates sha1-derived names, not qgr7mj: # .\provision-shared-tf.cmd --name-hash "" --plan-only

T7 — apply = make Azure match the plan (Benefit: declarative converge)

Theory: Apply executes the plan and writes IDs into state. Re-run is idempotent when state matches Azure (0 to add). Use on a sandbox / greenfield hash — not on live rg-shared-class1 without import.

cd D:\azure # TRAINER ONLY — greenfield or after import. Do NOT run on live shared estate without §E import. .\provision-shared-tf.cmd --auto-approve

T8 — for_each + outputs (Benefit: HCL loops)

Theory: One resource block with for_each creates bronze/silver/gold/audit containers. Outputs mirror Bicep output names so later app scripts can use the same labels.

cd D:\azure notepad infra\terraform\shared-eastus\main.tf # Search for: azurerm_storage_container.medallion # Search for: output "storageAccountName" # After a successful apply/import you can print outputs: # cd infra\terraform\shared-eastus # terraform output

T9 — After either IaC: same app release (not Terraform)

Theory: IaC builds the kitchen. Notebooks and ADF pipelines are the recipes — still shipped with release.cmd. Switching Bicep ↔ Terraform does not change the CI/CD conveyor for app code.

cd D:\azure .\deploy-shared-lab.cmd .\release.cmd adf .\release.cmd medallion-deploy .\release.cmd verify
